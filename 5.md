## 1. HIGH — E2E no puede matar procesos ajenos

Problema actual: en `tests/AtlasNOC.Tests.E2E/E2EFlowsTests.cs` existe lógica `KillPortListener()` que busca procesos escuchando en el puerto E2E y los termina con `Kill(entireProcessTree: true)`.

Corrección obligatoria:
- Elimina `KillPortListener()` y cualquier equivalente que mate procesos ajenos.
- Usa puerto dinámico/libre, puerto exclusivo del fixture, o termina únicamente `_server`, es decir, el proceso creado y poseído por el fixture.
- El fixture sólo puede finalizar procesos cuyo PID/proceso haya creado él mismo.

Prueba:
- Ejecuta E2E dos veces consecutivas.
- Debe arrancar, cerrar y volver a arrancar sin matar procesos externos ni dejar listener residual.

## 2. HIGH — outage E2E debe venir de LAB/probe, no fabricar estado en DB

Problema actual: el flujo de caída/alerta modifica directamente estado operacional mediante EF:
- crea `AlertRule`;
- inserta `MetricSample`;
- pone el dispositivo en `DeviceStatus.Down`.

Eso prueba parcialmente alertas, pero no demuestra:
`red/probe -> polling -> estado -> alerta -> incidente -> recovery`.

Corrección obligatoria:
- Revisa y usa `ILabNetworkControl`, probe/simulador LAB, `LabMode` o mecanismo equivalente real.
- Flujo esperado:
  1. dispositivo sano;
  2. polling sano;
  3. provocar outage desde LAB/probe;
  4. esperar polling real;
  5. verificar cambio de estado;
  6. esperar alerta;
  7. verificar incidente;
  8. restaurar conectividad;
  9. esperar recovery;
  10. verificar resolución/estado recuperado.

Permitido:
- consultar DB para asserts.

Prohibido:
- insertar manualmente la métrica de fallo;
- cambiar directamente `DeviceStatus` para fabricar el evento.

Si la regla de alerta no tiene aún un flujo UI/API apropiado, documenta esa excepción, pero outage y recovery deben venir de la capa LAB.

## 3. MEDIUM — Data Protection sólo permisivo en Development y Testing

Problema actual: la lógica basada sólo en `IsProduction()` deja Staging permisivo.

Política requerida:
- Development -> permitido para dev;
- Testing -> permitido de forma controlada;
- Production -> certificado obligatorio;
- Staging -> certificado obligatorio;
- otros -> fail-closed salvo justificación explícita.

Implementación sugerida:
```csharp
var isDevOrTest =
    builder.Environment.IsDevelopment() ||
    builder.Environment.IsEnvironment("Testing");

if (!isDevOrTest)
{
    // thumbprint obligatorio
    // certificado obligatorio
}
```

Tests mínimos:
- Development sin thumbprint -> arranca.
- Testing sin thumbprint -> arranca.
- Production sin thumbprint -> falla.
- Production thumbprint inválido -> falla.
- Staging sin thumbprint -> falla.
- Staging thumbprint inválido -> falla.

## 4. MEDIUM — rate limiter debe usar identidad coherente

Problema actual: `UseRateLimiter()` está antes de `UseAuthentication()`, por lo que `HttpContext.User` puede no estar autenticado aún.

Corrección preferida:
```csharp
app.UseAuthentication();
app.UseRateLimiter();
app.UseAuthorization();
```

Particionado:
1. usuario humano autenticado -> identificador estable;
2. API key autenticada -> `api_key_id`;
3. fallback anónimo -> IP efectiva validada.

Nunca usar API key cruda como partition key.

Tests:
- usuarios distintos -> particiones distintas;
- API keys distintas -> particiones distintas;
- sin auth -> IP;
- cabecera vacía -> nunca partición `""`;
- API key cruda no aparece en logs/estado.
